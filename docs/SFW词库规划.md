# ComfyChair H3 · SFW 词库整体规划

> 版本：v7（2026-11-18）—— 补 14 项缺口：男性描述与双人互动（§1.2）、SFW 风格串与负向（§1.5）、派生文件隔离（§1.1.1）、导入不做内容拦截（§2.5）、lint 白名单与全量断言（§4.3）、诚实边界（§8）；清理 §7 待定项
> 目标：在不改动现有引擎算法的前提下，新增一套 SFW 词库，覆盖词库组合与剧情组合两条链路。
> **核心约束（v2 定稿）：两库互斥**——开关开启只抽 NSFW，关闭只抽 SFW，任何一次输出都不混合两种内容。

---

## 0. 现状基线（只读核实）

| 文件 | 结构 |
|---|---|
| `assets/tag_catalog.json` (252 KB) | 顶层 `version / categories / rules / constraints / schemaVersion / meta / anchors`；41 个分类，每分类 `{id,label,group,tier,who,slots[{id,label,pool[],excluded}]}`；词是纯字符串池 |
| `assets/story_catalog.json` (172 KB) | 顶层 `schemaVersion / version / note / casts / pools / templates`；`pools` 26 个键（world/time/style/hair/build/bust/accent/place/outfit/outfit_state/outfit_mid/chore/escalate/pose/act/act_finish/prop/detail/mood/socks/shoes/man_look/man_outfit/man_state/ethnicity/skin） |
| `storage/TagLibraryStore.kt` | 单文件名 `tag_catalog.json` + `.base` + `.backup` + `.pinned` + 资产种子；支持 导入(合并/覆盖)/导出/单槽位更新 |
| `storage/StoryLibraryStore.kt` | 同构，固定 `story_catalog.json` |
| `TagComposerEngine` | 抽取、`repair()`（冲突重抽）、`allowed()`（前提过滤）、`handCap/handCost`（手占用预算）、`skipCategories/skipWords`（互斥） |
| `StoryGenerator` | 字段常量 27 个（CAST/HAIR/ETHNICITY/…/ACT/FINISH/PROP/WORLD/STYLE）；`randomize(picks, only)` 支持按字段子集重抽 |

结论：**SFW 不需要新引擎，只需要一套同 schema 的数据 + 一个内容级别（profile）开关 + 少量过滤与提示**。

## 1. 词库结构

### 1.1 双资产并行，不混在同一个文件

```
assets/tag_catalog.json          ← 现网 NSFW（不动）
assets/story_catalog.json        ← 现网 NSFW（不动）
assets/tag_catalog_sfw.json      ← 新增
assets/story_catalog_sfw.json    ← 新增
```

- 沿用同一 `schemaVersion = 1`，避免解析器分叉。
- `meta` 新增两个字段：
  - `"profile": "sfw" | "nsfw"`（导入时校验，防止把 NSFW 词库导进 SFW 档）
  - `"rating": "general" | "mature"`（用于 UI 角标与导出提示）
- `TagLibraryStore` / `StoryLibraryStore` 增加 profile 维度：文件名变为 `tag_catalog.sfw.json` 等，方法与现有一致（`importFrom / exportTo / updateSlot / resetToDefault` 全部复用，只是前缀不同）。

#### 1.1.1 派生文件必须整套派生（v7 补，防返工）

`TagLibraryStore` 现有 6 个文件名是写死常量（`TagLibraryStore.kt:252-257`）：

```
tag_catalog.json          工作副本
tag_catalog.base.json     内置基线（用于判断内置是否更新）
tag_catalog.backup.json   每次写入前的备份
tag_catalog.pinned        用户导入过整包则置位，此后内置更新不再覆盖
tag_catalog.previous.json 上一版内置（种子/回滚）
```

**只给工作副本加后缀是错的**：两档会共用 `.pinned` 与 `.backup`，结果是一档导入后另一档也被钉住、备份互相覆盖。要求：

1. 6 个文件名由 `profile` 统一派生（`tag_catalog.sfw.json` / `tag_catalog.sfw.base.json` / …），不允许逐个 if 判断。
2. `StoryLibraryStore` 同构处理。
3. `assets` 侧资产名同样派生：`tag_catalog.json` ↔ `tag_catalog_sfw.json`，`story_catalog.json` ↔ `story_catalog_sfw.json`。
4. **内置更新按档独立比对**：`base` 与内置的 version/revision 只在同 profile 内比较。否则 NSFW 的内置更新会被判定为「SFW 已是最新」而吞掉，或反向把 SFW 基线覆盖成 NSFW 内容。
5. 迁移：老用户只有 NSFW 档文件，首次运行 SFW 档时 SFW 侧无文件是**正常状态**（走内置种子），不得回落到 NSFW 文件——回落即污染。这一条要写单测。

**为什么不走"单文件加字段过滤"**：词条是纯字符串池，加标记要整体改 schema 与导入导出；而且用户自建/导入的词库无法判断级别，混在一个文件里迟早漏词。双文件边界清楚，审核也只看一个文件。

### 1.2 分类集合（SFW 侧）

保留并重写（词面全部去性化）：`people / race / person / featureHead / eyeColor / hair / top / bottom / outfitState / bodyType / waist / hips / legs / skin / socks / shoes / garment / headwear / jewelry / makeup / pose / activity / handAction / expression / gazeDir / headPose / scene / camera / mood / grade`

删除（SFW 下不存在）：`pussy / penis / bra / panties / breasts / nipples / fluids / toys / sexAct / maleBody / maleHand`

新增 SFW 专属（现有 NSFW 词库没有、但日常题材需要的）：`weather（天气）/ season（季节）/ light（光线时刻）/ occupation（职业）/ hobby（爱好）/ pet（宠物）/ propObject（生活物件）/ composition（构图）/ lens（镜头焦段）/ film（画质质感）/ emotion（情绪）/ age（年龄段，仅 20s–40s）/ maleFeature（男性面部与体格）/ interaction（双人互动）`

**v7 新增的两类，各堵一个洞**

| 分类 | 为什么必须有 | 兜底后果（不做的话） |
|---|---|---|
| `maleFeature` | SFW 删掉了 `maleBody` / `maleHand`；剧情侧 `man_look` / `man_outfit` / `man_state` 也只覆盖后两项。选「一男一女」时男方只剩一个"一位男子" | 双人图男方永远是同一张脸、同一个身材，且无法重抽 |
| `interaction` | 「关系」分类已定删除，双人画面就失去了"怎么在一起"的词 | 两人同框却没互动，构图只能靠姿势硬猜，容易出背靠背站桩 |

- `maleFeature` 词池 ≥ 16 条，与 `featureHead` 一一对位（脸型 / 眉眼 / 鼻唇 / 胡须 / 体格 / 年龄感），措辞不含任何解剖描写。
- `interaction` 词池 ≥ 18 条，全部是**动作短语**而非关系称谓：并肩走过、共撑一把伞、递过一杯咖啡、十指相扣、从背后轻轻抱住、背靠背看书、同看一部手机、替对方拨开额发、一起搬起纸箱、并肩坐在台阶上。
- `interaction` 只在 `people ∈ {一男一女, 两女}` 时可抽，`people = 单人` 下由 `allowed` 直接排除，不靠 `skipCategories` 硬跳。

> `people` 在 SFW 下限定「单人 / 两人 / 三人」，去掉「一男多女 / 多个女孩」等组合。

**判定口径（v5 定稿）：露骨才算 NSFW，性感属于 SFW。**

判定只看**是否露出或描写性器官与性行为**，不看是否奇幻、是否性感、是否挑逗。

| 保留（SFW，允许） | 剔除（NSFW，禁止） |
|---|---|
| 魅魔、精灵、兽人、天使、恶魔、吸血鬼等幻想种族 | 裸露的乳房、生殖器 |
| 性感姿态：倚墙、回眸、咬唇、撩发、抬腿、跪坐 | 性行为及其过程描写 |
| 贴身衣物：紧身针织裙、包臀裙、深 V、开衩、露背、吊带 | 体液（精液、爱液等） |
| 内衣外穿、泳装、运动背心、短裤 | 性玩具、自慰、插入类动作 |
| 媚态、慵懒、撩人、暗示性表情 | 明确性交体位与交合动作 |
| 「身材丰满」「曲线分明」这类体型描述 | 「赤裸」「全裸」「仅着内衣」这类暴露状态 |

- 即：`魅魔，身着深色长裙` 留；`魅魔，性感姿态` 也留；`魅魔，赤裸` 不留（改写或删除）。
- 内衣/泳装类词条：**允许存在，但必须带完整穿着**（如"黑色蕾丝内衣套装"），不得写成"只穿内裤"这类残缺状态。
- 「内衣外穿」与「仅着内衣」是两件事，别混：前者是内衣当外衣搭配（**允许**），后者是身上只剩内衣（**禁**）。所以 lint 必须按**完整词条**匹配，不许按单词「内衣」一刀切。
- 一句话记法：**看得到的是衣服，就不是 NSFW；看到的是器官，才是。**

### 1.3 规则文件

`rules` 与 `constraints` 在 SFW 版**必须重写一份**，不能沿用 NSFW 的：

- `singletons`：改为 SFW 的单值互斥词（如「全身雨湿」「戴着帽子」「室内」「夜景」）。
- `skipCategories`：保留机制，内容改为「穿外套 → 跳过内搭细节」「戴帽子 → 跳过发型细节」「雨天 → 跳过干燥地面类场景词」。
- `skipWords`：SFW 里基本用不到，留空数组即可。
- `constraints.handCost`：只保留日常动作（撑伞、拿咖啡、扶栏杆、抱猫…），`handCap` 仍为 2。
- `constraints` 其余键保持默认，不引入新的约束类型。
- `anchors.families`：SFW 只保留 3 个族——`portrait（肖像）/ fullbody（全身）/ scene（场景叙事）`，各族给 `express / gaze / camera / outfitState` 四个维度，用于风格一致性。

### 1.4 输出顺序

`meta.promptTiers` 在 SFW 下按「主体 → 衣着 → 姿态 → 场景 → 光线 → 镜头」重排，并把新增分类插进合适层：

```
0: race, person, age, bodyType, hair, eyeColor, maleFeature
1: top, bottom, outfitState, socks, shoes, headwear, jewelry, makeup, garment
2: expression, gazeDir, headPose, pose, activity, handAction, interaction
3: scene, weather, season, light, propObject, pet, occupation
4: camera, lens, composition, mood, grade, film, emotion, style
```

`interaction` 排在 2 层末尾（动作层），保证「姿势 → 互动 → 场景」的叙事推进不被打断。

### 1.5 SFW 风格串与负向提示词（v7 新增）

两处内容不在 `categories` 里，但同样会被拼进最终提示词，必须各备一份。

**风格串（`meta.stylePrompt`）**

现网六层结构不变（媒介画质 / 角色设计语言 / 线条笔触 / 明暗档数 / 色彩方向 / 质感细节），但 SFW 版整份重写：

- 删除所有以情色摄影为卖点的媒介描述（私房、暗房裸拍、软色情写真等）。
- 保留并扩写真/街拍/时装/纪实/风景/静物/日常 vlog 帧这些方向。
- 判定口径仍按旧规矩：看阴影边界锐度与档数分档，不靠高光形态。

**负向提示词**

| 档 | 内容 |
|---|---|
| NSFW | 沿用现状不动 |
| SFW | 换成通用缺陷项：模糊、低分辨率、畸变、多余肢体、错误手指、文字水印、logo、压缩噪点、过曝死白 |

SFW 负向**不再需要**任何 nsfw / nude / censored 类词条——SFW 档本来就不会生成那些内容，留着纯属浪费 token；同时也避免负向词与正向词互相拉扯导致画面变僵。

## 2. 与现有词库及引擎的衔接

### 2.1 互斥开关（v2 定稿）

**形态**：一个「成人内容」二态药丸。开 = 只用 NSFW 库；关 = 只用 SFW 库。没有"混合"这一档。

**位置（v6 定稿）：并进现有的「增强 · 去重 ▾」下拉菜单**，不新增独立药丸。

- 菜单里现有三条（增强模式 / 普通模式 / 近期去重）+ 一条新增：**「NSFW 词库」**，右侧是开关，副文案「关闭后只用 SFW 词库，不混出」。
- 药丸标题带上当前档位：`增强 · 去重 · 成人 ▾` / `增强 · 去重 · SFW ▾`。
- **SFW 态时「单人 / 多人」选择框变淡绿**（选中项底色淡绿 + 淡绿描边，文字转深绿），作为档位的整体视觉标识；药丸本身同时变淡绿。
- 剧情组合顶部放同款状态标识（同一开关的另一入口），两处共享同一状态。
- 设置页不放——那里太深，用户每次要切都要爬三层。

**默认值**：老用户默认「开」（保持现状不突变），新装默认「关」，**不弹询问**。

**为什么互斥优于混库**：

1. **可验证**：关掉后能对 SFW 资产做整包断言——「可渲染词并集 ∩ 禁词表 = ∅」，一条 lint 就能证明，而混库按权重抽永远无法证明"这一次不会抽出露骨词"。
2. **心智简单**：用户看到开关就知道结果，不需要理解"概率"。
3. **导出干净**：分享/备份出去的配置天然只有一种级别。

**切换时的处理（关键）**：不是简单清空，而是**白名单式过滤**——

- 逐字段检查当前值是否存在于目标库的同 id 池中：在 → 保留；不在 → 移除并计数。
- 结束时提示「已切换为 SFW，移除了 N 项不适用的内容」。比全清空友好，且严格保证零残留。
- 分类 id 相同但池不同的（种族、场景、风格等）必须走这套检查：同名分类在两边可能是不同词表，不能假定兼容。

**自动化断言**（写进 CI / lint）：

- SFW 档下所有分类 pool ∪ 剧情 pools 的并集，与 `forbidden_nsfw.txt` 禁词表求交，必须为空；
- 反向：NSFW 档的并集必须与 SFW 独有词表交集为空以外的检查不做（不要求）。

**首次切档说明卡（v7 补）**

触发条件：用户第一次把开关从「开」拨到「关」，且此后不再重复弹出（存一个 `seen_sfw_intro` 布尔）。

文案定稿：

```
已切到 SFW

• 性感还在：深 V、开衩、咬唇、泳装这些都保留
• 只去掉露骨：性器官、性行为、体液
• 不移除历史：图库与已提交的任务不受影响
```

最后一条必须留——否则用户会以为关了开关就等于换了安全模型（见 §8.1）。卡片底部一个「知道了」即可，不做二次确认、不做"以后再说"。

切回 NSFW **不**弹任何卡片，避免来回拨时被打扰。

**长期说明入口（v7 定稿，宿主已存在）**

一次性卡片只解决"第一次切"的困惑；日常想知道"到底管什么"的入口，放在**已有的 `详细说明 ›`** 里，不新建帮助页、不往设置页塞。

- 现有实现：`TagComposerScreen.kt` 的 `GuardPill` 菜单最后一项 `详细说明 ›` 打开 `GuardDetailDialog`，标题「三盏开关各管什么」，正文由 `GuardBlock(tag, accent, headline, lines)` 堆叠。
- 加 NSFW 词库后本来就是四盏，**补第四块即可**，标题改「四盏开关各管什么」，引导语改「上面两盏每次只能亮一盏，下面两盏各自开关」。
- 第四块文案（定稿，照现有口语风格，可直接粘）：

```
tag      = "NSFW 词库"
accent   = MaterialTheme.colorScheme.error（仅做区分，不用红色告警语义）
headline = "关掉就只用 SFW 词库，两边不混"
lines    = listOf(
             "开着只抽成人词，关掉只抽日常词，同一次输出不会一半一半",
             "关掉后这些还留着：深 V、开衩、露背、泳装、咬唇 —— 性感算日常，只去掉露骨",
             "管不到自己手写的词，也管不到设置里自己填的系统提示词",
             "模型没换，关开关不等于换安全模型"
           )
```

- 第四块不做"了解更多"跳转，点「知道了」关闭即可——现有弹窗就是这个交互，不引入新层级。

### 2.2 范围边界（v2 新增，必须明确）

开关管的是「词库抽取」。下面三处它管不到，必须逐条给出结论——有 SFW 版、不新建、还是拦在入口——否则开关就是假的安全感：

| 模块 | 现状 | 需要 |
|---|---|---|
| 剧情组合模板 | `story_catalog.json` 的模板句本身含性描写 | SFW 四模板独立提供（见 §3.3） |
| AI 提示词优化的系统提示词 | 内置 `prompt_expert.md` 实测露骨词命中 0（通用翻译器，非 NSFW 专用）；设置里另有**用户自填**的系统提示词 | **不新建 SFW 版**：内置那套本身通用，用户自填属外部输入、不在开关管辖内（见 §8.1） |
| 用户自建/导入词库 | 可能含任意内容 | 导入进 SFW 档必须先过 lint，否则拒绝 |

**明确不管**：图库已有的历史图片/视频、已提交的队列任务。开关只影响"从现在起抽什么"，不删除任何既有内容。

### 2.3 自动补词（空槽位补词）

- 引擎按 `categories` 遍历，SFW 没有的分类自然不参与，无需改代码。
- `promptTiers` 决定输出顺序，SFW 用自己的一份，不会出现"跳层的词跑到前面"。
- 补词时按 SFW 的 `pool` 抽取，天然不会补出露骨词——**这是双文件方案最大的收益**。

### 2.4 冲突替换（`repair()`）

- 机制不变：选中某词后，冲突的非空槽位会被重抽，并按上次改动加提示「「性行为」因冲突已换词」。
- SFW 版 `skipCategories` 里若引用了不存在的分类 id（例如沿用 NSFW 规则时误带 `sexAct`），引擎现有的按 id 过滤会直接跳过，**不会崩**；但仍要求 SFW 规则里不出现已删除分类，由 lint 保证。
- SFW 下不存在"性行为"这类冲突源，实际触发频率会显著低于 NSFW。

### 2.5 存档与导入导出

- 存档键仍是 `分类id.槽位id`。从 NSFW 切到 SFW 时，遇到当前词库不存在的键：**保留在存档里不删，只在渲染时忽略**，并提示「有 N 项在当前内容级别下不可用，已隐藏」。切回去可恢复。
- 导出文件带 `meta.profile`；导入时若级别不符，给出明确提示并拒绝合并（避免污染）。
- **导入不做内容拦截**（v8 定稿）：SFW 档是「默认内容分级」，不是安全沙箱。用户拿自己的词库来用就照收，拒收只会被当成导入功能坏了。合并同样不拦，也不置 pinned。
- 词库升级（现有"内置更新自动换新并保留自定义词"机制）对 SFW 资产同样适用，两条线各自独立升级。

**导出与识别（v7 补）**

- 导出默认文件名带档位：`tag_catalog_sfw.json` / `tag_catalog.json`，`story_catalog_sfw.json` / `story_catalog.json`。用户同时存两份也不至于分不清。

## 3. 剧情组合的适配（含分项名重抽）

### 3.1 字段表随级别变化

`StoryGenerator` 的 27 个字段常量中，SFW 只启用：

```
CAST / ETHNICITY / HAIR / SKIN / BUILD / BUST(改称"体态") / ACCENT / MAN_LOOK / MAN_OUTFIT / MAN_STATE
TIME / PLACE / WORLD / OUTFIT / STATE / SOCKS / SHOES / CHORE / POSE / DETAIL / MOOD / STYLE
```

不启用（SFW 下没有候选池）：`ESCALATE / MID / ACT / INTER / FINISH / PROP`

- 界面按"当前词库是否有该分项的候选池"决定是否渲染该行，而不是硬编码隐藏——这样以后 SFW 想扩也只改数据。
- 姿势/动作本来合成一行；SFW 没有 `ACT` 时，该行只显示「姿势」，重抽也只抽姿势，不再成对。

### 3.2 分项名点击重抽（与词库组合一致的三层入口）

| 入口 | SFW 下的行为 |
|---|---|
| 分项名（如「种族」） | 只重抽该分项；候选池来自 SFW 剧情池 |
| 分区标题「整段重抽」 | 只重抽该分区内**存在且未锁定**的分项 |
| 词条点击 | 打开候选抽屉；候选来自 SFW 池 |

新增两条必须有的反馈（当前缺失）：

1. 该分项在 SFW 下**没有候选池** → 提示「当前内容级别下没有可重抽的选项」（而不是静默无反应）。
2. 该分项**全部被锁定** → 提示「该分项已锁定，先解锁再重抽」。

防冲突仍然走 `StoryGenerator.randomize(only)` 内部的 `allowed()`，不做任何绕过。

### 3.3 SFW 剧情模板（必做，v2 确认）

`story_catalog_sfw.json` 提供 4 个模板（`solo / mf / mff / ff`）的 SFW 版本——**剧情组合与词库组合都做 SFW 版**，不是"剧情沿用 NSFW 模板再过滤"：

- 场景叙事（通勤、咖啡馆、图书馆、海边、居家、街头摄影…）
- 不含任何性行为描写、不含衣物脱离过程、不含体液
- 保留"人物标准句式 + 场景 + 光线 + 镜头"的结构，与 NSFW 模板同构，便于以后互转

### 3.4 分项池清单（v6 补、v7 修订，B4 施工依据）

**现状实测**：`story_catalog.json` 共 26 个池 / 1010 词；模板只用到 13 个占位符，句式是

```
{time}{world}{cast}在{place}。{female} {male} {escalate}，{outfit_mid}，拿着{prop}，{pose}，{acts}，{detail}。

SFW 模板把 `{escalate}{outfit_mid}{prop}{acts}` 整段拿掉，换成 `{chore}` + `{pose}` + `{detail}` 三段叙事，并新增 `{light}` 一句：

```
{time}{world}{cast}在{place}。{female} {male} 正在{chore}，{pose}，{light}，{detail}。

**v7 补充决策：剧情侧不新增 `interaction` 池，也不改 `StoryGenerator` 字段常量。**

理由与做法：

1. SFW 模板句式已经是 `…{female} {male} 正在{chore}，{pose}，{light}，{detail}。`——双人互动天然落在 `{chore}` 位（"一起冲咖啡""并肩走过多雨的街道""共撑一把伞"），再单开一个字段会导致 `chore` 与 `interaction` 二选一，句式反而别扭。
2. 加字段要动 `StoryGenerator` 的 27 个常量与模板占位符解析，属于「不改引擎」红线的边缘，不值得。
3. 由数据侧解决：SFW `chore` 池里约 1/3 标 `who=duo`，`cast = solo` 时由 `allowed` 过滤掉。这条要求写进 `check_sfw.py`：`chore` 池中 `who=duo` 的条数须 ≥ 40。
4. `maleFeature` 在剧情侧不需要新增——`man_look` 已覆盖男性外貌，扩到 16 词即可。

**与词库组合的对应关系**（保持两边概念一致，便于用户理解）

| 种族 / 发型 / 体型 / 皮肤 | `ethnicity` / `hair` / `build` / `skin` | 同上 |
| 姿态 / 动作 | `pose` / `chore` | 剧情侧是"叙事里的动作"，比词库侧更完整成句 |
| 场景 / 天气 / 季节 / 光线时刻 | `place` / `world` / `time` / `light` | 剧情侧合并成 `place` + `world` + `time` + `light` 四个池 |
| 风格 / 光影色调 | `style`（模板外置） | 剧情风格独立于词库风格串 |

### 4.2 清洗流程（从参考包到我们的池）

1. **剔除**：`NSFW` 整类、`负面提示` 类、任何含露骨词的字面。
2. **去角色名**：grimoire 的 `日漫女角色(297)/日漫男角色(214)/游戏女角色(183)` 是具体作品角色名，**全部剔除**（版权 + 与我们的"身份/职业"语义不符）。
3. **改写**：英文短句 → 中文自然句；紧凑 label（`站·重心后脚★`）→ 完整短句（`重心落在后脚，前膝放松`）；去掉 `★` 等标记。
4. **去重**：同义合并（`柔和光线` / `柔光` 取一条，另一条作别名）。
5. **分档**：按 S1 日常 / S2 时尚 / S3 运动 标注。
6. **过 lint**：见 4.3，不通过不入池。

### 4.3 审核标准（机器 + 人工）

**机器 lint（新增 `tools/check_sfw.py`，随词库一起版本化）**

1. 禁词正则：解剖词、性行为动词、体液、暴力、药物、仇恨、未成年相关（含「学生 / 萝莉 / 少女 / 童」等歧义字一律拦截，改写为「成年女性 / 年轻女性」）。**顺序是先禁后白**：命中禁词后，再看是否整条命中 `allow_sfw.txt` 白名单；白名单只放完整词条，不放词，避免"改一个词就绕过"。
2. 每条提示词必须含年龄锚（`adult` 或「成年」）。
3. 服装完整性：`top` 与 `bottom` 至少一个非空，或 `garment` 为连衣裙类；**只拦"裸露/赤裸/仅着内衣"这类残缺状态，不拦"紧身/深 V/开衩/露背/吊带/泳装"这类性感穿着**。
4. 人数上限 ≤ 3，且不出现多男结构。
5. 每个 `pool` ≥ 12 条（低于此值重抽会明显重复）。
6. 分类 `label` 与词条语言一致（全中文），不含英文裸词。
7. 交叉冲突：`rules` 引用的分类 id 必须存在；`constraints.handCost` 的键必须能在某个 pool 中找到。
8. **跨分类重复**（v7 补）：同一词条出现在两个分类的池里要报错，除非显式登记为别名。否则「柔光」在 `light` 与 `grade` 各有一份，会出现同句重复。
9. **场景-着装穿帮**（v7 补）：见 §4.4，属于数据规则检查，不与禁词混在一起跑。

**白名单 `allow_sfw.txt`（v7 补，必须有）**

只有禁词正则时，合规词会被误杀——参考包实测里，「胸部以上取景」「曲线分明」「皮肤通透」「深 V 领」都被裸解剖词正则命中过（魔导书 19 条误命中就是这么来的）。

- 白名单文件与禁词表同目录，一行一条**完整词条**，命中即放行并记入 `allow_hits.log`。
- 白名单条数超过总量的 3% 视为异常，需人工复核——白名单一旦变成垃圾桶，lint 就失效了。

**禁词表单一是硬要求（v7 补）**

`tools/forbidden_nsfw.txt` 是**唯一**禁词来源：

- `check_sfw.py` 读它；
- App 运行时切档断言也读它（打包进 assets，`assets/forbidden_nsfw.txt`）；
- 两份内容由构建脚本校验一致，不一致直接构建失败。

不允许脚本里再手写一份内联正则——那必然与运行时漂移，出现"脚本说 0 错、App 还在抽"。

### 4.4 场景与着装联动（v7 补，S3 默认开的必要条件）

运动/泳装已定默认开启，那就必须约束它们出现在对的场景里，否则会出「办公室穿比基尼」。

| 着装 / 状态 | 允许场景 | 禁止场景 |
|---|---|---|
| 泳装 / 比基尼 | 海边、泳池、浴室、游艇、沙滩 | 办公室、图书馆、地铁、会议室 |
| 运动背心 / 瑜伽裤 | 健身房、公园、居家、跑道 | 礼服晚宴、教堂、正式会议 |
| 礼服 / 长裙 | 晚宴、剧院、婚礼、宴会厅 | 健身、浴室、街头跑步 |
| 居家服 / 睡衣 | 居家、卧室、阳台、清晨厨房 | 办公、正式外景 |

实现方式两条并用：

1. 数据侧：给这些词条打 `allowed` 场景白名单（引擎已有前提过滤能力，不改算法）。
2. 校验侧：`check_sfw.py` 加一条交叉检查——任一"强绑定着装"词对应的场景池若为空，报错。

同理，`interaction` 与 `people` 的绑定（单人不抽互动）也在此节登记，由 lint 校验。

**人工二审**

- 逐条通读，标注强度：`S1 日常`（通勤/居家/咖啡）、`S2 时尚`（街拍/写真/时装）、`S3 运动`（健身/泳装/户外）。默认全开；不想要时用词库窗口**现成的「忽略」**把对应分类关掉即可，不新增强度总开关（§7 已定开关只在模式菜单，不再往设置页加东西）。
- 二审只做减法：可疑即删，不做"看起来还行"的保留。

## 8. 边界与已知限制（v7 新增，对外文案底稿）

开关承诺的是**一句很窄的话**：从这一刻起，App 自己抽出来、拼进去的提示词里不含露骨内容。超出这句的部分明确不管，否则就是给了假的安全感。

**受众标注（v7 补，别混）**

| 小节 | 受众 | 去处 |
|---|---|---|
| 8.1 管不到的三处 | **用户** | 已收回 §2.1「长期说明入口」，成为 App 内第四块 `GuardBlock` 文案 |
| 8.2 已核实的工程事实 | **只有开发** | 留在本文档，不进 App、不进更新说明 |
| 8.3 不承诺 | **用户**（前两条）/ 开发（第三条） | 前两条并入说明卡与第四块文案；第三条留文档 |

本节保留为**对外文案的底稿与依据**：改 App 文案先改这里，再改代码，避免两处说法不一致。

### 8.1 管不到的三处

| 位置 | 现状 | 说明 |
|---|---|---|
| 用户手写 / 手动输入的提示词 | 生成页有自由文本输入框 | 不拦、不过滤，用户写什么发什么 |
| 用户自填的系统提示词 | 设置 › 提示词 › 系统提示词编辑器 | 属用户配置，SFW 档不替换也不改写 |

第三条尤其要在说明卡里写清：**关掉开关 ≠ 换成安全模型**。要真正出干净图，得同时换模型；这一版不做模型切换。

### 8.2 已核实的工程事实（可写进说明、不怕被质疑）

- 客户端源码中**没有**任何写死的露骨提示词串。全量检索命中的都是代码注释，以及 `StoryGenerator` 里基于「全裸」的判定分支（如 `man_outfit == "全裸"`、`contains("赤裸")`）。
- SFW 词库不含「全裸」这类词，因此这些判定在 SFW 档恒为 false——不崩、无害，属可接受的死分支，不专门清理（清理会牵动穿脱状态机，收益不足）。
- 因此 SFW 档不会被 App 自身污染，风险只集中在 8.1 的三处外部输入。

### 8.3 不承诺

- 不承诺「绝对不可能生成任何擦边内容」——模型对「深 V」「开衩」「咬唇」这类合规词仍可能给出较性感的结果，这是既定口径（性感属 SFW），不是缺陷。
- 不承诺历史内容变化：图库已有的图片视频、已提交的队列任务不受影响。
- 不承诺跨设备一致：词库是本地文件，用户在两台设备上可能处于不同档位。
